## 产品定位

Notch AI Monitor 是一个围绕 MacBook 刘海区域呈现的 AI CLI 会话监视器。它面向同时运行多个 AI 编程/自动化会话的用户，在不占用主要屏幕空间的前提下，提示最需要用户介入的会话状态。

一句话价值：

> 默认隐入刘海，不打扰；只有 AI 会话需要用户判断、收取结果、处理错误或确认风险时，才用最小可见面积提醒用户。

## 目标用户

- 同时运行 Claude CLI、Codex CLI、Qwen CLI 等多个 AI 工具的开发者。
- 用 AI agent 执行长任务、脚本生成、自动化发布或批处理任务的创作者/工程师。
- 需要在多个终端、项目、任务之间切换，但不想被普通运行状态持续打扰的用户。

## 核心用户目标

1. 一眼知道有没有需要我处理的 AI 会话。
2. 快速区分普通等待、完成、失败和高风险事件。
3. 在最短鼠标移动距离内定位到相关会话。
4. 对风险命令、失败重试、结果查看等动作做出明确判断。
5. 在没事发生时，让产品几乎不可见。

## 核心概念

### 状态

| 状态 | 用户感知 | 产品含义 |
| --- | --- | --- |
| 休眠 Dormant | 只看到刘海里的淡线/睡眠眼 | 没有需要用户处理的事 |
| 一瞥 Glance | 胶囊露出小角标 | 有事件，但不紧急 |
| 探出 Peek | 胶囊完整展开，表情变亮 | 用户悬停查看，或风险事件主动探出 |
| 展开 Expanded | 面板落下 | 用户处理具体事项 |

### 情绪/事件

| 情绪 | 场景 | 静息状态 | 优先级 |
| --- | --- | --- | --- |
| 无 none | 全部会话正常 | 休眠 | 最低 |
| 开心 happy | 结果已完成 | 一瞥 | 低 |
| 难过 sad | 出错或超时 | 一瞥 | 中 |
| 等待 waiting | 需要用户确认 | 一瞥 | 中高 |
| 愤怒 angry | 高风险命令/危险操作 | 探出 | 最高 |

当前状态机实现位于 [prototype/interactive-v2.js](../prototype/interactive-v2.js)，核心规则是 `restingStateForMood()`：`none -> dormant`、`angry -> peek`、其他情绪进入 `glance`。

## 当前原型覆盖范围

原型已经覆盖：

- 刘海固定不变，左右胶囊从刘海后方滑出。
- 左胶囊展示会话聚合入口。
- 右胶囊展示当前最需要关注的提醒。
- 动作面板展示当前会话、提示语、分页、定位/查看按钮。
- 会话面板展示 Claude、Codex、Qwen 三个 mock 会话。
- 演示控制台可切换情绪和状态。

原型尚未覆盖：

- 真实 CLI 会话接入。
- 真实事件队列、分页、确认、拒绝、重试、查看日志。
- 设置页、权限授权、通知偏好、隐私策略。
- 键盘操作、屏幕阅读器体验、减少动画偏好。
- 小窗口/窄屏布局。

## 当前原型的主要不足

### 1. 产品价值还停留在演示层，缺少真实数据模型

现在所有会话、时间、状态、事件数量都是 mock。产品要成立，下一步需要定义真实事件 schema：

- 会话来源：工具名、终端名、项目名、窗口句柄。
- 会话状态：运行中、等待确认、完成、失败、超时、风险拦截。
- 事件内容：标题、正文、命令、风险原因、创建时间、优先级。
- 动作结果：已查看、已定位、已批准、已拒绝、已重试、已忽略。

没有这层模型，界面无法判断什么应该露出、什么应该隐藏。

### 2. “只显示需要注意的事”与左胶囊常驻存在概念冲突

效果说明强调普通运行不抢占空间，但等待/风险时左胶囊仍展示 Claude 运行时间。这个设计可以成立，但需要明确规则：

- 如果左胶囊是“后台运行概览”，它是否应该在所有非休眠状态都显示？
- 如果产品主张是“只显示需要处理的事”，左胶囊是否应该默认隐藏，只在用户悬停或展开时出现？
- 当右侧有高风险事件时，左侧普通运行信息是否会分散注意力？

建议下一版把左胶囊定义成“辅助入口”，默认在 `glance` 中保持更弱，或只在 `peek/expanded` 中出现。

### 3. 悬停触发不稳定，需要修正命中区域

代码把 `mouseenter` 绑定在 `#notchZone`，但 `.notch-zone` 本身高度为 `0`，实际可命中区域依赖内部绝对/普通子元素。浏览器取证中，等待状态下移动到刘海区域后仍停留在 `glance`。

建议：

- 给 `.notch-zone` 明确的 hover hit area，例如 44-56px 高度。
- 用透明 hit target 覆盖刘海下缘，避免用户必须精准对准胶囊。
- 增加自动化测试：等待状态 hover 刘海后应进入 `peek`，移开后回到 `glance`。

### 4. 关键动作语义不足

操作面板目前只有“定位”和“查看”。但不同事件需要不同动作：

- 等待确认：批准、拒绝、查看命令、复制命令、定位终端。
- 结果就绪：打开结果、复制摘要、标记已读。
- 出错/超时：查看日志、重试、终止、忽略。
- 风险拦截：查看完整命令、查看风险原因、拒绝、允许一次、加入规则。

下一版应让 CTA 跟随事件类型变化，而不是所有状态共用一组按钮。

### 5. 风险场景缺少信任与安全细节

风险状态目前只显示“风险待处理”和“危险命令”。用户真正需要判断的是：

- 危险命令是什么？
- 为什么被判定危险？
- 会影响哪些路径、权限或进程？
- 是否可以撤销？
- 是 AI 自动生成、用户触发，还是第三方脚本触发？

风险类产品不能只靠红色和表情提醒，需要提供可验证证据。

### 6. 多事件队列只是视觉占位

右胶囊显示 `2`，面板里有“第 1 / 2 项”和上一条/下一条按钮，但分页按钮没有真实行为。Tabs 也只是视觉状态，不能切换会话内容。

建议补齐：

- 事件队列数据结构。
- 当前事件 index。
- 上一条/下一条切换。
- 每个会话自己的待处理事件数。
- 处理后自动跳到下一条或收起。

### 7. 可访问性风险明显

当前原型的可访问性还没有产品化：

- HTML `lang="en"`，但主体内容是中文，应改为 `zh-CN`。
- 面板状态变化没有 `aria-live` 或等价通知。
- 胶囊依赖颜色、表情和位置变化，缺少文本状态补充。
- 没有明显键盘焦点样式。
- 悬停是关键入口，但键盘用户没有等价入口。
- 多个动画没有 `prefers-reduced-motion` 分支。
- 表情元素 `aria-hidden` 可以接受，但右胶囊的可访问名称没有反映具体事件，例如“Qwen CLI 等待确认，2 项待办”。

### 8. 响应式和窗口尺寸处理不足

窄视口下，胶囊和面板都按刘海中心点固定锚定，未做 `clamp()` 或边界避让：

- `390px` 宽时左胶囊从 `x=-23` 开始，部分不可见。
- 操作面板宽 `320px`，从 `x=292` 开始，右侧大面积溢出。
- 会话面板也会从屏幕左侧溢出。

如果产品只面向 MacBook 桌面，也仍需处理：

- 外接显示器无刘海。
- 小窗口预览。
- 缩放比例变化。
- 刘海尺寸差异。

### 9. 演示控制台和产品体验混在同一画面

演示控制台对评审有用，但它不是产品本体。当前截图里左下角控制台非常抢眼，会让评审者误以为它是正式功能。

建议把 demo harness 拆出：

- `interactive.html` 专注正式体验。
- `demo.html` 或 debug 参数显示控制台。
- 产品文档截图优先使用无控制台版本。

### 10. 产品形态和安装路径未定义

目前还不清楚 Notch AI Monitor 是：

- macOS 菜单栏应用？
- 浏览器/网页原型？
- CLI companion？
- Electron/Tauri 桌面应用？
- 与终端进程通信的后台 agent？

这会影响权限、通知、窗口层级、刘海定位、进程监控和用户信任。下一版产品文档需要明确技术形态。

## 建议下一版优先级

### P0：先让产品逻辑成立

- 定义真实会话/事件数据模型。
- 定义事件优先级与去重规则。
- 为等待、完成、错误、风险分别设计动作集合。
- 补齐风险事件详情：命令、原因、来源、影响范围、允许/拒绝。
- 修复 hover hit area，并增加 hover/keyboard 等价入口。
- 增加面板边界避让，避免窄屏和小窗口溢出。

### P1：让原型可被真实评审

- 拆分正式原型和演示控制台。
- 补齐事件队列分页、会话 tabs、处理后状态流转。
- 给左胶囊制定清晰规则：什么时候出现、出现什么、优先级低于右侧提醒。
- 加入键盘焦点、`aria-live`、`lang="zh-CN"`、`prefers-reduced-motion`。
- 为每个状态加入空状态、已处理状态、失败恢复状态。

### P2：增强产品质感

- 替换字母缩写图标为真实或更可识别的工具图标。
- 加入细粒度通知偏好：仅风险主动探出、完成自动收回、等待延迟提醒等。
- 支持外接显示器/无刘海模式，改为菜单栏胶囊或屏幕顶部悬浮。
- 增加 onboarding：选择监控哪些 CLI、授权方式、隐私说明。

## 下一步建议

最值得立刻做的一版不是继续加视觉效果，而是做“产品化 MVP”：

1. 把 demo 数据抽成事件模型。
2. 修复 hover、键盘和窄屏边界。
3. 让右侧操作面板根据事件类型展示真实动作。
4. 把演示控制台移到 debug 模式。
5. 为风险事件补一个可信的详情面板。

这样产品会从“漂亮的状态演示”变成“可以被用户真实试用和反馈的工作流原型”。
